# Project synchronization contract

The hook talks only to `/api/v1/projects/{project_id}/publish`, `/context`, and `/acknowledgements` using a project-scoped bearer credential. Enrollment mints or accepts the harness credential one of three ways, dispatched in this order by what the private form was submitted with:

1. **A portal-minted credential** (form field `credential`): a token already minted in the service's web portal (Account menu → Manage my harnesses) is pasted in directly. It is verified with the least side-effecting authenticated call available -- a `publish` with `{"operations": []}` -- and, if not rejected with 401/403, stored as-is. No `/api/login`, no Entra token, no `/api/harnesses` call at all; the token is exactly what the portal minted.
2. **Microsoft sign-in (`az login`)**, only when the credential and member-code fields are both blank and the service advertises Entra bearer support (see below): an Entra bearer token is minted via `POST /api/harnesses`.
3. **A short-lived member cookie** (via `/api/login`), the fallback: requesting `context:read`, `session:write` and `shared:write`.

Whichever path is used, the member login code (when entered) and the portal credential are never persisted anywhere but the private connection file; the pasted-in-plaintext form field itself is never echoed or logged. Each project requires its own connection.

The default service base URL is the Amplifier Online web origin, `https://amplifier-teamwork-web.livelysea-7d934004.westus2.azurecontainerapps.io`. An explicitly selected trusted custom HTTPS service URL is permitted, but this is not a compatibility guarantee for an arbitrary service. Service URLs reject userinfo, query, and fragment components; HTTP is permitted only for literal loopback test hosts (`localhost`, `127.0.0.1`, or `::1`). The retired origin `team.amplifier.run` is refused deterministically and without any network call: a session configured against it stays inert and reports a one-line hint to update and reconnect, and a `410` from the service during an active session maps to the same hint.

### Entra (Microsoft sign-in) enrollment

**This path requires the service to validate Entra bearer JWTs on `/api/harnesses` and to advertise `api_app_id` via `/api/config`; both are pending server-side work as of this writing.** Until then, `GET /api/config` either does not advertise a non-empty `api_app_id`, or is itself gated by the service's own auth layer (see below) -- either way the practical effect is the same: Microsoft sign-in enrollment is not offered, and the form falls back to the portal-credential or member-code fields.

`GET /api/config` (unauthenticated per the plan) advertises `{tenant_id, api_app_id}` when Entra bearer support is live; an empty or unreachable `api_app_id` means Microsoft sign-in is not offered. **Any failure fetching it -- a 401/403 from an auth layer in front of the service, a timeout on a cold origin, or any other transport error -- is tolerated as "unavailable," never a hard enrollment failure**: it is treated identically to the service explicitly not advertising `api_app_id`. When sign-in is available, `POST /api/harnesses` is called with an Entra access token in the request's authorization header, and either a `repository_url` (canonical URL from this directory's git remote, when no project ID was typed) or an `X-Teamwork-Project` header (when one was). A `409` response means the repository does not identify exactly one project; the caller is asked to type one of the returned candidate project IDs. A `401`/`403` means the signed-in identity did not map to a Teamwork member; the member-code fields remain available in the same form.

Because the project is not always known before this mint, the usual reserve-then-mint file ordering inverts for this path: the credential is minted first, then the local connection file is reserved. If a saved connection already exists for the resulting project, the newly minted credential is revoked (same authorization) and the existing saved connection is reused untouched -- an existing saved connection is never overwritten, regardless of which enrollment path is used. Stored `connection.json` gains one optional field, `repository_url`, recording the canonical repository URL for this project so `teamwork_bind` can resolve it later without a network call; a connection stored via the portal-credential path also sets `harness_id: null`, since no harness was minted locally to hold that ID.

`teamwork_bind`'s network `discover` fallback (used when no locally saved connection matches the git remote) applies the same tolerance: a 401/403 from that endpoint is reported as "discovery not available on this service yet," distinct from "reached the service, no matching project," and neither case raises.

Authenticated HTTP requests refuse redirects. Each request has a 30-second timeout; a synchronization failure preserves queued work and never fabricates a receipt.

If interruption falls between input attachment and durable receipt commit, the exact prepared candidate is retained in the local journal as `acceptance_unknown`, including after the interrupted turn is closed. The replay helper reports unresolved outcomes even before a session resumes. These candidates are not published as accepted hook injections and never generate speculative receipts.
