# Project synchronization contract

The hook talks only to `/api/v1/projects/{project_id}/publish`, `/context`, and `/acknowledgements` using a project-scoped bearer credential. Enrollment mints or accepts the harness credential one of three ways, dispatched in this order by what the private form was submitted with:

1. **A portal-minted credential** (form field `credential`): a token already minted in the service's web portal (Account menu → Harnesses & agents) is pasted in directly. It is verified with the least side-effecting authenticated call available -- a `publish` with `{"operations": []}` against the typed project. Empirically, this endpoint validates auth and project scope before it ever inspects the operations list, so a genuinely valid token scoped to that project returns `422 invalid_request` ("Supply 1-20 operations") -- not 2xx; an invalid token returns `401` regardless of project, and a valid token against the wrong project returns `404`. Only `422` (or an outright `2xx`, should that ever change) is treated as verified; `401`/`403` is an explicit rejection; anything else -- `404`, `5xx`, or a transport failure -- proves nothing and is reported as "could not verify," never silently accepted. On success the token is stored as-is. No `/api/login`, no Entra token, no `/api/harnesses` call at all. If a connection is already saved for that project, the pasted credential is not used -- an existing saved connection is never overwritten -- and the form says so explicitly, with how to rotate (revoke the old harness, delete the saved file, reconnect).
2. **Microsoft sign-in (`az login`)**, only when the credential and member-code fields are both blank and the service advertises Entra bearer support (see below): an Entra bearer token is minted via `POST /api/harnesses`.
3. **A short-lived member cookie** (via `/api/login`), the fallback: requesting `context:read`, `session:write` and `shared:write`.

Whichever path is used, the member login code (when entered) and the portal credential are never persisted anywhere but the private connection file; the pasted-in-plaintext form field itself is never echoed or logged. Each project requires its own connection.

The default service base URL is the project's own domain, `https://teamwork.amplifier.ms` -- the same value the service publishes at `/api/config` as `share_url`, and the value its member plane gates the `Origin` header on. An explicitly selected trusted custom HTTPS service URL is permitted, but this is not a compatibility guarantee for an arbitrary service. Service URLs reject userinfo, query, and fragment components; HTTP is permitted only for literal loopback test hosts (`localhost`, `127.0.0.1`, or `::1`). The retired origin `team.amplifier.run` is refused deterministically and without any network call: a session configured against it stays inert and reports a one-line hint to update and reconnect, and a `410` from the service during an active session maps to the same hint.

### Entra (Microsoft sign-in) enrollment

Service discovery and successful Entra enrollment are separate checks:

- **Service discovery verified, 2026-09-17:** the canonical `/api/config` returns non-empty `api_app_id` and `tenant_id`, plus `auth_mode: "sso"`, `auth_required`, and `project_id`.
- **Live enrollment refusal reported in [PR #48](https://github.com/michaeljabbour/amplifier-bundle-teamwork/pull/48):** `_mint_sso` received `403 not_a_member` after obtaining a token for the advertised audience and tenant. In the current server, this error is emitted after JWT validation when the selected email identity is absent from the operator-managed roster's `email`/`aliases` map. It does not establish that all accounts fail; reconcile the affected token identity with that roster. Updating a profile's persisted email alone does not update this bootstrap roster gate.
- **Member-code enrollment:** PR #48 reports a successful live enrollment and credential creation. This path remains available when Microsoft sign-in is refused.

The setup script's project discovery change does not change Entra token validation or roster authorization.

`GET /api/config` (unauthenticated per the plan) advertises `{tenant_id, api_app_id}` when Entra bearer support is live; an empty or unreachable `api_app_id` means Microsoft sign-in is not offered. **A 401/403 fetching it -- an auth layer gating the service in front of its own code -- is tolerated as "unavailable," never a hard enrollment failure**: it is treated identically to the service explicitly not advertising `api_app_id`. Any OTHER failure (DNS, TLS, connection refused, timeout, 5xx) is a genuine service-reachability problem, not an SSO-configuration signal, and is surfaced as a clear, retryable error naming only the service host -- never the full URL or any path -- so a typo'd or unreachable `base_url` is never misdiagnosed as "SSO not enabled." When sign-in is available, `POST /api/harnesses` is called with an Entra access token in the request's authorization header, and either a `repository_url` (canonical URL from this directory's git remote, when no project ID was typed) or an `X-Teamwork-Project` header (when one was). A `409` response means the repository does not identify exactly one project; the caller is asked to type one of the returned candidate project IDs. A `401`/`403` means the signed-in identity did not map to a Teamwork member; the member-code fields remain available in the same form.

Because the project is not always known before this mint, the usual reserve-then-mint file ordering inverts for this path: the credential is minted first, then the local connection file is reserved. If a saved connection already exists for the resulting project, the newly minted credential is revoked (same authorization) and the existing saved connection is reused untouched -- an existing saved connection is never overwritten, regardless of which enrollment path is used. Stored `connection.json` gains one optional field, `repository_url`, recording the canonical repository URL for this project so `teamwork_bind` can resolve it later without a network call; a connection stored via the portal-credential path also sets `harness_id: null`, since no harness was minted locally to hold that ID.

`teamwork_bind`'s network `discover` fallback (used when no locally saved connection matches the git remote) applies the same tolerance: a 401/403 from that endpoint is reported as "discovery not available on this service yet," distinct from "reached the service, no matching project," and neither case raises.

Authenticated HTTP requests refuse redirects. Each request has a 30-second timeout; a synchronization failure preserves queued work and never fabricates a receipt.

If interruption falls between input attachment and durable receipt commit, the exact prepared candidate is retained in the local journal as `acceptance_unknown`, including after the interrupted turn is closed. The replay helper reports unresolved outcomes even before a session resumes. These candidates are not published as accepted hook injections and never generate speculative receipts.

### Messages

A `message.upsert` publish op's `data` addresses exactly one recipient, using exactly one of `to_agent_id`, `to_node_label`, or `to_person`; supplying zero or more than one is refused (`422 invalid_request`) before the service looks at anything else. `to_node_label` and `to_person` are resolved by the service against currently-live agents only (case-insensitive exact match on the declared node label, or on the owning person's name) -- an address that matches nobody currently live is refused the same non-disclosing way as an unknown `to_agent_id` (`404 not_found`), and one that matches more than one live agent is refused as `409 ambiguous_recipient` with a bounded `candidates` list (`agent_id`, `node_label`, `owner`) so the sender can retry by agent id. Whichever key was used to address it, the stored record and every subsequent read carry only `to_agent_id`; the alias keys never persist.

`/context` responses additionally carry a top-level, bounded `message_status` array (present only when `"messages"` is requested in `selection.include`): the sending session's own last 20 outbound messages, newest first, each with `state` \u2208 `queued | delivered | accepted` derived server-side from delivery and acknowledgement, never from anything the client asserts. This array sits alongside `items`, never inside it -- a sender is never handed its own outbound message as something to receive, acknowledge, or file.

### Local queue observations

An `agent.upsert` may carry a bounded `queue` object: `queue_status` (exactly one of `ready`, `stale`, `unavailable`), `observed_at`, an optional `ready_count`, an optional `integration` name and an optional `reason_code`. It is `harness_observed` in the service's own provenance map — our word about what the local work-tracker CLI told us, stamped with when it told us. `stale` is a reading that succeeded once and could not be refreshed: it keeps the ORIGINAL `observed_at`, so its age is visible rather than disguised. An absent `queue` means nothing was shared, never "this machine has no tracker". Filesystem paths, command lines, queue names and host names are not in the allow-list and cannot be sent: every outbound payload passes through `reports.sanitize_outbound`, which drops any key it does not recognise.

### Declared waiting

A `presence.upsert` with `state: "waiting"` must carry a non-empty `reason` of at most 200 characters; the service refuses a waiting state without one. The reason lives on the presence record, which expires the same way presence always has, and it is dropped the moment the session reports any other state — a wait that outlives the waiting is worse than no wait at all. The `teamwork_wait` tool is the only producer: it declares, and it notifies nobody, assigns nobody and creates no dependency. Host approval events, where an orchestrator emits them, corroborate a declaration; they are not required for one.

**Why it is declared and not detected.** No runtime signal exists on this host that says a turn is blocked on a person. The kernel emits nothing for it, and the installed orchestrator may or may not raise an approval event — a constant existing upstream is not evidence of a producer. The one alternative, inferring it from elapsed silence, would report `waiting` for a model that is merely slow, which is a lie of exactly the kind the rest of this protocol refuses. So nothing is inferred and no timer exists anywhere in this path.

To detect rather than declare, a runtime would have to emit a signal that says three things at once: that the turn has stopped, that it stopped **pending a person** rather than pending a tool or a provider, and **which** person or decision it stopped on. A bare "turn idle" event is not enough — it cannot separate a blocked turn from a slow one, which is the whole distinction this state exists to carry. Until such a signal exists, a declaration from the session is the only honest producer, and `teamwork_wait` is it.

### Projected work

A projected item is a `work.upsert` carrying one `external` evidence reference: `{"kind": "external", "uri": "worktracker://<queue>/<item-id>", "label": …, "revision": …}`. `external` is a distinct evidence kind from `artifact` precisely because `artifact` requires an http(s) URL that a reader may follow, and this locator has nothing behind it — a view renders it as text, never as a link.

The shared record id is derived from the local id (`worktracker-<item-id>`), so republishing the same item is the same record rather than a second one. Concurrency is the service's ordinary `expected_version` rule: the session writes at the version it read, a record a person has since edited answers `409 version_conflict`, and the tool reports "re-read it and retry" for that item while the rest of the batch proceeds. Nothing is ever overwritten to resolve a conflict.

Projection bookkeeping — when it was last projected, at which source revision, by whom — is kept in the service's `_sync` side-index and exposed read-only through `GET /api/project-view`. It is deliberately not on the work record: writing it there would bump `version` on every reprojection and make every reader's `expected_version` stale for a fact no person edited.
